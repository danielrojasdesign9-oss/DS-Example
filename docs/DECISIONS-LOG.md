# ClickGuard Decision Log

This log records the product and implementation decisions made for the Threat Monitoring prototype. Entries are tagged **instructed** when they follow Daniel’s signed brief, **improvised** when the prototype needed a small implementation choice, and **questioned** when two reasonable options were considered and one was selected.

| Decision | Who | Why | Discarded alternative |
|---|---|---|---|
| **[instructed]** Use a light enterprise skin with semantic red only for blocked or malicious states. | Daniel | Marketing teams need clarity without feeling like they are operating a SOC console; red must retain meaning. | A dark-first security dashboard with red accents throughout. |
| **[instructed]** Treat the timeline as the reasoning trail, with evidence attached to the visit where it happened. | Daniel | Cumulative blocking becomes legible when the client can follow the journey chronologically. | A detached “why we blocked” explanation panel. |
| **[instructed]** Keep verdicts qualitative and reserve numbers for labeled diagnostics. | Daniel | Raw model percentages create false precision; clients need a human sentence, confidence in words, and a falsifiable prognosis. | Showing bot probability as the primary verdict. |
| **[instructed]** Use Watching, Blocked, and Trusted, with a filterable gray “Needs a look” sub-level. | Daniel | Ambiguity is a first-class state and color cannot be the only channel. | A binary blocked / allowed model. |
| **[instructed]** Apply the converter-unblock rule automatically and narrate both phases. | Daniel | A real purchase is stronger evidence than a preliminary bot pattern. The system must be reversible and honest about its reassessment. | Keeping a converted visitor blocked until manual review. |
| **[instructed]** Compute Spend avoided from the paid-visit cost values of excluded visitors. | Daniel | Money shown in the KPI strip must be auditable, not a made-up marketing label. | Hardcoding a headline dollar value. |
| **[instructed]** Show a qualitative risk band in the table and put the numeric diagnostic only in the drawer. | Daniel | This keeps the scan understandable while allowing deeper investigation. | Putting a 0–100 score in the table for fast comparison. |
| **[instructed]** Keep the visitor table populated by default, including first-timers. | Daniel | Fresh traffic is the normal state; invisibility would undermine trust. | A threat-only table that hides Watching visitors. |
| **[instructed]** Make the drawer the home of visitor actions and use Radix Dialog behavior. | Daniel | Focus management, Esc-to-close, and focus return are essential for a minutes-long investigation. | Navigating to a separate visitor route. |
| **[instructed]** Use a pnpm monorepo with `packages/ui` and `apps/web`; keep domain types out of the design system. | Daniel | The design system must be reusable and generic while the app owns ClickGuard mechanics. | Defining domain models inside the UI package. |
| **[instructed]** Generate CSS token output from a single `tokens.ts` source. | Daniel | Preventing token drift between TypeScript and CSS makes the system auditable. | Maintaining CSS variables and TS constants independently. |
| **[instructed]** Use compact 8-column table rows, sortable headers, bulk actions, CSV export, and undo. | Daniel | The primary task is to trust fast, then verify deeply; operators need efficient scanning and reversible controls. | A spacious card grid with no bulk workflow. |
| **[improvised]** Use a synthesized 44-visitor dataset so the prototype feels populated while still covering the required edge states. | Manus | The signed contract asked for 40–60 visitors; 44 provides enough scan density without making the preview unwieldy. | A much smaller hand-authored set that would not exercise sorting or pagination affordances. |
| **[improvised]** Use reserved documentation IP ranges and recognizable ISP names. | Manus | The dataset needs deterministic, safe identifiers while preserving the “visitor by IP” mechanic. | Using real customer-looking IP addresses. |
| **[questioned]** Display the derived monitoring count (32) instead of the brief’s illustrative 328. | Manus | The prototype’s KPIs are more trustworthy when they reconcile to the visible dataset rather than pretending the mock data represents a larger account. | Hardcoding 328 visitors despite only 44 visible records. |
| **[improvised]** Treat the first visible row as the first-timer by default sort because `lastUpdated` is the default order. | Manus | Recent monitoring traffic should appear first, and the single-visit row proves the “never empty” rule immediately. | Hiding first-timers behind a special onboarding route. |
| **[instructed]** Preserve the raw-to-qualitative chain and D4 conflict chain in the reasoning trail. | Daniel | These are the trust-building aha moments: diagnostic clues become a human verdict, and a purchase becomes a visible automatic unblock. | Silently changing a status with no explanation. |
| **[improvised]** Keep Storybook stories in the UI package while the WebDev preview remains the app delivery surface. | Manus | The session supports a working frontend preview and a checked-in Storybook source; account-connected Chromatic deployment remains a later handoff. | Building a second disconnected component demo. |
